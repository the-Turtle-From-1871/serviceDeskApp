## Backend Architecture & Feature Constraints


### 🔐 Capabilities — the authorization unit
Access is decided by a `Capability`, never by a role comparison. Nine values: `VIEW_INVENTORY`, `VIEW_ALL_RECEIPTS`, `CREATE_RECEIPTS`, `EDIT_ITEM_HOLDER`, `MANAGE_ITEMS`, `MANAGE_QUEUE`, `PROCESS_RETURNS`, `VIEW_ANALYTICS`, `ADMINISTER`.
* **A role is a BASELINE set, not a check.** `VIEWER` → `VIEW_INVENTORY`; `USER` → that plus `VIEW_ALL_RECEIPTS`, `CREATE_RECEIPTS`, `EDIT_ITEM_HOLDER`; `ADMIN` → all nine. `UserCapability` rows **add** to the baseline, so one person can be given just the service queue without being made an admin.
* **Grants are additive only — there is no negative grant.** A subtractive model makes the effective set depend on the order two tables are read in, and the wrong answer to "does a deny beat a grant?" is a privilege bug. To reduce an account below its baseline, change its **role**.
* **`src/modules/users/capabilities.ts` is the SINGLE definition** of the role→capability mapping, and is pure (`import type` only, no Prisma runtime import) so it unit-tests without a database — the same reason `readiness.ts` is split out. Do not restate the mapping in SQL, in a component, or in a test helper: a second copy is a second answer to "what can this person do", and they will disagree.
* **The effective set is resolved in exactly ONE place** — `defaultGetSession` in `src/lib/authz.ts` — and rides along on the query that already re-reads `role`/`isActive`. One query, no N+1, and a revoked grant dies on the next request. The JWT deliberately never carries capabilities: a token minted before a grant would be stale, and per-request freshness is what makes the 30-day session window affordable. `getCurrentUser` (`src/lib/session.ts`) resolves the same set through the same pure function for RENDERING only — it is not a boundary.
* **`requireAdmin()` is a thin alias for `requireCapability("ADMINISTER")`.** Keep it for the genuinely administrative surfaces (users, audit, contact book, named signatures, access PIN, receipt timers, seal verification); call `requireCapability` directly for anything narrower — `MANAGE_ITEMS`, `MANAGE_QUEUE`, `PROCESS_RETURNS`, `VIEW_ANALYTICS`.
* **`setItemsCategoryAction` takes `MANAGE_ITEMS`, not `MANAGE_QUEUE`**, despite living in `readiness.ts` — it assigns a device category, which is item vocabulary. The file it sits in is historical, not a statement about which capability owns it.

* **Permission requests** (`permissions.service.ts`): one request, one justification, many capability lines decided individually. The admin decides by UNCHECKING — an absent capability in the approve set is a denial, not an omission.
  * **`decidePermissionRequest` refuses a decision by the requester.** The self-grant guard on `ADMINISTER`; the only failure in this module that is a security bug rather than a usability wart. Its test must not be weakened.
  * Grants use `createMany({ skipDuplicates: true })` inside the decision transaction — idempotent, and race-safe against two admins deciding overlapping requests.
  * **Approving `ADMINISTER` (labelled "Grant Administrator") PROMOTES the account to the `ADMIN` role instead of writing grant rows.** Granting it as a capability produced `{VIEW_INVENTORY, ADMINISTER}` on a `VIEWER` — past every `requireAdmin()` gate but refused `MANAGE_ITEMS`/`CREATE_RECEIPTS`/`VIEW_ANALYTICS`, and still rendered "User" on `/admin/users`, which shows the ROLE. **A promoting decision writes NO `UserCapability` rows, including for the other approved lines on the same request**: the `ADMIN` baseline covers all nine, and a grant row OUTLIVES the role, so a later demotion would leave admin silently in place — breaking "to reduce an account below its baseline, change its role". The promotion runs in the same transaction as the line decisions and is idempotent. The self-decision guard above is what keeps this from being self-promotion; it matters more now, not less.
  * A denial requires a reason, stored on the REQUEST (one reason covers the batch). A capability already held or already pending cannot be requested; a DENIED one can be requested again.
  * **The requester's justification is OPTIONAL and has no minimum length** (a 20-character floor was removed 2026-08-10 — it refused short-but-real reasons and produced padded text instead of better ones). It is trimmed, capped at 2000, and defaults to `""`. Do not reinstate a floor in the schema *or* as a `minLength`/`required` on the textarea — a browser-side constraint there refuses to submit the form at all. Both surfaces that render it (`/account`, `/admin/permissions`) must handle blank; the admin queue shows "No reason given" rather than empty quotes. **The denial reason is unaffected and stays required** — the two are different fields answering different questions.

### 🤖 Service & Ticket Lifecycles
* **A blank service deadline means NO deadline on CREATE, and NO CHANGE on UPDATE.** These are different questions and the code answers them with two functions. `computeServiceDueAt(from, days)` owns creation and returns `null` for a blank. `serviceDueAtUpdate(days, from)` owns updates and returns **`{}` — an empty object — for a blank, so `dueAt` never appears in the UPDATE at all.** That is what makes a no-op re-save exactly stable: the column is not recomputed, not re-based on `now`, not read-modify-written. **Clearing an existing deadline is deliberately not expressible through either** — it is reachable only via `setServiceDeadline` / `setServiceDeadlineAction`, behind the item page's own "Update deadline" control.
  * **Why not prefill the days input instead:** the store holds an absolute instant while the input means *days from now*. Any prefill drifts — a 7-day deadline set 3 days ago prefills as 4, and saving unchanged pushes it out again, every time. Not writing the column is the only exactly-stable representation. This mirrors the hand-receipt return timer (`setReceiptDueAtAction` / `ReceiptDueAtControls`), which is a dedicated single-purpose form for the same reason.
  * The old per-type `SLA_DAYS` table (REIMAGE 3 / REPAIR 7 / OTHER 5) was **deleted**: an invisible server-side default produced overdue emails and "Overdue Nd" badges for work nobody had put a date on. **If a default is ever wanted back, it must be a visible, clearable prefill in the flag UI — not a server-side substitution.**
  * `parseOverrideDays` stays deliberately graceful (blank, `0`, negative, decimal, non-numeric and >3650 all collapse to "no deadline") so one bad value can never block a receipt build, a flag, or a reopen. **The one exception is `setServiceDeadlineAction`**, which REJECTS an out-of-range value with a message instead of treating it as blank — it is the destructive control, so a typo must not read as "wipe it".
  * **A NEW ROUND resets; an edit to a LIVE request does not.** `completeServiceItem` deliberately leaves the finished round's `dueAt`/`overdueAlertedAt` on the row, so both paths out of `COMPLETED` must clear them first: `upsertServiceRequest` wipes a `COMPLETED` row (`updateMany` scoped to that status, inside the same transaction, **before** the upsert) and `reopenServiceItem` always writes `dueAt` afresh. Otherwise a device that broke a second time inherited the first job's deadline — opening as "Overdue 17d" — and its alert stamp, which the sweep's `overdueAlertedAt: null` filter turns into *this lapse can never alert*. Regression tests guard both; do not relax them back to "blank leaves the deadline alone" on those paths.
  * `overdueAlertedAt` is re-armed **only when `dueAt` is actually written**, so editing a note cannot re-send the overdue email for a deadline that already alerted.
  * `setServiceDeadline` is scoped to `status: "PENDING"` — a deadline on completed work measures nothing, and the form is only rendered for a pending request, so a completed row reaching it could only be a crafted POST.
  * Consumers already guard on `dueAt: { not: null, ... }`, so a deadline-less item is never overdue-alerted, never lands in the dashboard's due lists, renders as `—`, and sorts last in the Due column in BOTH directions.
* **Immutable Closed State:** Once a ticket status transitions to "Closed", it becomes entirely immutable (cannot be reopened, edited, or modified).
* **90-Day Purge:** Tickets must automatically calculate an expiration timestamp exactly 90 days after closing. A background worker must permanently delete these records upon expiration.
* **DCSIM Notifications:** Entities are identified as "DCSIM" via a checkbox/boolean field. The "Notify for pickup" UI button must be completely hidden if the recipient isn't DCSIM, paired with backend validation to reject non-DCSIM notification events.


### 🤖 Operational Readiness & Analytics
* **Readiness AND accountability are both DERIVED — neither is a stored state.**
  * **Readiness** ("can it go out") is computed from live signals by `readinessState()` in `src/modules/items/readiness.ts`: `RETIRED` (lifecycle) > `IN_REPAIR` (a `PENDING` `ServiceQueueItem`) > `DEPLOYED` (an open unreturned hand receipt) > `READY_TO_DEPLOY` (`markedReadyAt` set) > `DEPLOYED` (an MDM `lastLogonUserPrincipalName`) > `UNTRIAGED`. **That precedence is load-bearing** — checking the service flag before the receipt rule is what stops a device turned in for repair on an still-open receipt from reading "Deployed".
    * **A hand-set signal is never overridden by MDM telemetry — only by a deliberate act** (service flag, open receipt, retirement). A `DEPLOYED` rule reading `lastLogonAt > markedReadyAt` sat between the receipt rule and `READY_TO_DEPLOY` and was **removed**: a device on our own shelf produces logons routinely (imaging it, an MDM check-in, a test before reissue), so it read "Deployed" while physically in hand, contradicting the person who had just held it. Automated nightly imports made that a next-morning problem rather than a weekly one. What it uniquely caught was an issue-out with **no** hand receipt; a documented one is already rule 3. `lastLogonAt` is still parsed and stored, so reinstating the rule is a one-line change if undocumented issues become common — but re-add it to **both** twins or `readiness.parity.test.ts` fails.
  * **Accountability** ("do we physically have it") is derived from audit recency via `Item.lastAuditedAt` (`auditState` for one row, `auditCutoff` for the SQL aggregate; both share `AUDIT_PERIOD_YEARS`, so the badge and the dashboard can never disagree).
  * **Do NOT reintroduce a hand-tickable flag for either.** `Item.isAccountedFor` (`BOOLEAN NOT NULL DEFAULT true`) was dropped in `20260727234500_drop_is_accounted_for`, and the stored `Item.deployableStatus` enum + its `ItemStatusHistory` table were dropped in `20260728000000_derive_readiness`. Both measured a column default, not the fleet: production held 1,139 items with **zero** marked not-accounted-for, only **4** ever audited, and **0** with a readiness state ever set — so every device read "Untriaged" and the fleet read fully accounted for. Possession is claimed only where an audit proves it; readiness is claimed only where a live signal shows it.
* **`Item.markedReadyAt` is the ONLY hand-set readiness signal, and it is a TIMESTAMP on purpose.** It means "this device is back on my shelf as of now" (`markItemsReady`). The timestamp is what lets the marking be *compared* to other dated signals and what makes "when did we last have hands on this" answerable — it is **not** a self-expiry any more (the logon rule that expired it was removed; see the precedence note above). It now persists until a deliberate act supersedes it: an open hand receipt, a service flag, retirement, or an explicit clear (`clearItemsReady`). Never replace it with a boolean, and never backfill it from receipt state.
* **The readiness rule is written TWICE and kept honest by a test.** `readiness.ts` decides one row in TypeScript; `readiness.sql.ts` (`READINESS_CASE` / `READINESS_JOINS` / `readinessScope`) is the SQL twin the dashboard and the `/items` page use to bucket 1,100+ items in the database. `readiness.parity.test.ts` runs one fixture table through **both** and asserts they agree — change the precedence in one and that test fails until you change the other. Never add a third derivation: a surface that needs readiness calls `readinessForItems` (`readiness.query.ts`) or embeds the shared SQL fragments.
* **Readiness IS sortable in the `/items` table — through a second, raw-SQL query path, NOT a stored column.** Because it is derived from four signals across three tables there is nothing for a Prisma `orderBy` to name, so `listItems` branches: a sort whose keys include a **derived key** selects the ordered, paginated page of item **ids** with a parameterized `$queryRaw` (`READINESS_JOINS` + `READINESS_RANK` from `readiness.sql.ts`) and hydrates them with `getItemsByIds`; **every other sort stays on the untouched Prisma path**. The rank comes from `READINESS_ORDER`, so the sort follows the operational display sequence rather than alphabetising `IN_REPAIR` between `DEPLOYED` and `READY_TO_DEPLOY`. Both paths keep the `id` tie-break and the page-size cap, and the row count always comes from the one Prisma `count`.
  * **`auditState` is the OTHER derived key, and it takes the same raw path** (`DERIVED_SORT_KEYS` in `sort-keys.ts` is the set; `columnForKey` REFUSES both, so a caller that forgets to branch gets a typed error rather than a bad ORDER BY). It used to sit in `SORT_COLUMN` mapped to `Item.lastAuditedAt`, which sorted by raw **recency** while the column displays a three-value **badge**. Because a timestamp is very nearly unique per row — production carries 31 audited rows with **31 distinct stamps** — a secondary sort key had no ties to break, so picking "Audit, then Device name" silently ignored the second choice. It now ranks the badge via `auditRankSql` (`audit.sql.ts`), which gives each badge real ties for a secondary key to order within. **The rank sequence is `AUDIT_ORDER` in `audit.status.ts` — the SAME array the analytics donut stacks by** (`analytics.types.ts` re-exports it as `AUDIT_STATE_ORDER`; do not redeclare it, the palette's colourblind check was run against that exact order). The CASE has no `ELSE`, so a new `AuditState` missing from `AUDIT_ORDER` fails `audit.status.test.ts` rather than silently ranking `NULL`. Consequence: the Audit sort no longer orders by recency at all — inside a badge, order comes from your secondary key (then `id`).
  * **Do NOT resolve this by storing readiness on `Item`.** That is the `deployableStatus` column dropped in `20260728000000_derive_readiness`, and it is still forbidden above.
  * **The two paths each implement the `?q=` / `?uic=` filter, and two filter implementations drift.** `items.readiness-sort.parity.test.ts` seeds real rows and asserts both return the **same ids in the same order** for the same filters (none / search / UIC / both). Change the filter on one side without the other and it fails. The raw side must cast `"serialNumber"::text ILIKE` (citext + trigram index, see `searchItemsBySerial`) and must name **physical** columns — `currentUserEmail` is `@map("currentUser")`. Sort keys are spliced as identifiers, so they come from the `SORT_COLUMN` allowlist, never from the querystring.
    The `?q=` filter also spans a RELATION: it matches the recipient named on the item's current hand receipt (open, unreturned — the same custody rule `READINESS_CASE` uses for `DEPLOYED`, deliberately not `getHoldingTransfer`'s stricter latest-receipt rule, so search agrees with the Readiness badge beside it). On the Prisma side that is a nested `some`; on the raw side an `EXISTS` (`recipientMatchSql`). The recipient branch — and ONLY that branch — splits the query into whitespace tokens and ANDs them, so "doe jane" finds "Jane Doe"; both paths tokenize through `recipientTokens` in the leaf module `recipient-search.ts`, because two tokenizers would drift exactly like two filters.
* **There is no readiness timeline.** The "fleet status over time" chart was removed with `ItemStatusHistory`: derived state has no history, and replaying today's signals across an x-axis would fabricate a series. Reinstating it requires a deliberate periodic snapshot of the *derived* state — a new feature, not a query.
* **Completing a service-queue item stamps `markedReadyAt` in the same transaction** (`completeServiceItem`). The device is physically in hand at that moment; without the stamp it would leave `IN_REPAIR` straight back to whatever its stale MDM logon implies.
* **Categories are a MANAGED LIST with a DENORMALIZED value — deliberately not a foreign key.** `DeviceCategory` (citext-unique `name`) is the curated vocabulary admins maintain at `/admin/categories`; `Item.deviceCategory` stays a plain indexed **string**. The reason: a CSV import must be able to carry a category the property book has not registered yet, so an unknown category must never make an import fail. Keeping the two coherent is `categories.service.ts`'s job, and it does it two ways — **deletion is refused while any item still carries the name** (otherwise those devices hold a value that appears in no picker), and **imports register unseen names** (`learnCategories`, mirroring `learnUnits`). Do not "normalise" this into an FK without re-solving both. Changes to an item's category are logged to `ItemEdit` like `deviceUIC`.
  * **Normalization now runs at FIVE write sites** — CSV import, the admin edit page, the item card, the bulk selection-bar control, and the new-item form — and all five call `normalizeCategoryName` (from the pure `items.schema.ts`, never the `server-only` service) and then `learnCategories`. Miss either half at a new write site and you get the exact drift this design exists to prevent: an item holding a string that matches no vocabulary row, so the in-use count under-reports and an admin can delete a category still in use.
  * **`categoryOptional` is IMPORT-ONLY; edit forms use `categoryClearable`.** The former maps blank → `undefined`, which `diffItemFields` reads as "not submitted" — correct for a partial CSV, wrong for a form, where it made clearing the box a silent no-op that still reported "Saved". The latter keeps the blank string so the clear is recorded. Over-long names are *rejected* on the forms and still *dropped* on import, for the same reason.
  * **`categoryNew` is the CREATE form's variant** — blank → `undefined` like `categoryOptional` (a row that does not exist yet has no value to clear, and `""` in an indexed column is a value every filter counts), but over-long names are *rejected* like `categoryClearable`. Its trailing `.optional()` is load-bearing: `createItem` re-parses its own input at the service boundary, so the schema must accept its own output.
  * **A serial appearing TWICE IN ONE FILE resolves to the row with the newest `lastLogonDate`, not the first one** (`preferredCandidate` in `import.ts`). A re-imaged device is re-enrolled under a new device name while the old enrolment lingers, so the export carries both; first-wins was correct only because the export happens to be sorted newest-first, which nothing enforced or checked. Measured on the real fleet export: **29 such serials, every pair disagreeing, 4-208 days apart (median 41)** — so a change of export sort order would have silently written months-old device names and holders into the property book. `planImport` is therefore THREE phases: validate every row (so a malformed row can never win a contest and take a usable duplicate down with it), pick one winner per serial, then plan the winners. Precedence inside a contest: **usable** (a *new* serial's winner must carry make+model, or the device would be created by neither row) > **has a parseable date** > **newest date** > **earliest row**. That last tie-break is load-bearing, not tidiness: the scheduled Drive import skips a byte-identical file by content hash, so a plan that varied between runs on the same input would make `unchanged` meaningless. `skipped` is returned sorted by row and names which case applied.
  * **CSV header:** the category is filled from **`deviceType`** (also `deviceCategory` / `category`; `normalizeHeader` strips case and punctuation, so `Device Type` maps too). A bare **`type`** is deliberately NOT aliased — MDM exports carry a generic `Type` column of OS strings, and mapping it would overwrite every matched item's category and pollute the vocabulary. Keep the alias list explicit when adding new ones.
  * **Storage location** (`Item.storageLocation`) fills from **`SLoc`** (also `storageLocation` / `storageLoc`). A bare **`location`** is deliberately NOT aliased, for the same reason as a bare `type`: fleet exports carry a generic "Location" column meaning a geographic site, and aliasing it would overwrite every matched item's storage location and log the churn to `ItemEdit`. It is plain free text with no managed vocabulary and no index — unlike `deviceCategory`/`homeUnit`, nothing groups the fleet by it. Adding an importable column also means adding it to **`UPDATABLE_ITEM_COLUMNS`** in `items.service.ts` (the allowlist guarding the batched UPDATE's identifier splice) and to `loadExistingBySerial`'s `select`, or every import carrying it throws.
  * **Last sync** (`Item.lastSyncDateTime`) fills from **`LastSync`** (also `lastSyncDateTime` / `lastSyncDate`; `normalizeHeader` strips case and punctuation, so `Last Sync` and `last_sync` map too). A bare **`sync`** is deliberately NOT aliased, for the same reason as a bare `type` and a bare `location`: an export can spend that word on a sync STATUS ("Succeeded") rather than a timestamp. **It answers a different question from `lastLogonDate`** — when MDM last checked in, versus when a *person* last signed in; a device powered on in a cage syncs nightly with no logon for months, so the pair is what distinguishes alive-but-unused from gone. Three things about it are deliberate:
    - **It has NO parsed twin.** `lastLogonDate` has `lastLogonAt` because readiness and analytics compare it in SQL; nothing computes over the sync time, so a second column would be a denormalisation with no reader. The cost is that it **cannot be sorted or filtered**, which is why it is displayed but absent from `SORTABLE_COLUMNS` (see the `UNSORTABLE_COLUMNS` set in `items-view.ts`) — `ORDER BY` on the raw text sorts `10/1/2025` ahead of `7/25/2026`. Wanting a real sort means adding the twin, not an ORDER BY on the text.
    - **It updates SILENTLY** (`silentAfter` in `planImport`, like `enrollmentDate`/`compliance`) — and here that matters more than for the others: MDM syncs nearly every device nightly, so logging it would write ~1,200 `ItemEdit` rows a night and bury the custody edits the history exists to show. It still counts as a real change, so a row whose only difference is the sync time lands in `toUpdate`, not `unchanged`.
    - It is rendered **verbatim** on `/i/<id>`, in the `/items` phone card's More panel and as a toggleable desktop column — never reformatted, so it matches the MDM export people cross-check against.
* **Units are a MANAGED LIST with a DENORMALIZED value, exactly like categories — and the same two rules keep them coherent.** `Unit` (citext-unique `abbreviation`, managed at `/admin/units`) maps to a `fullName`; `Item.homeUnit` stays a plain string with **no FK and no index**, a denormalised copy of that `fullName`. So: **deletion is refused while any item's `homeUnit` still matches the full name**, and **renaming a unit backfills every item holding the old one** (`renameUnit`) — skip the backfill and the fleet holds two spellings of one unit, splitting it into two entries in the `/items` filter and two bars in the analytics leaderboard.
  * **Matching is case- and whitespace-insensitive** — `LOWER(btrim(...))` on both sides, values bound not spliced — and **all three comparison sites must agree**: `listUnitsWithCounts` (the item-count column), `renameUnit` (what gets rewritten) and `deleteUnit` (what counts as "in use"). Let one drift and the UI can report a unit as in-use while the delete succeeds anyway, orphaning devices onto a string that matches no picker. A consequence, not a bug: renaming also folds in items whose `homeUnit` differed from the old name only in case, since they're the same unit — those rows get an `ItemEdit` history row (`homeUnit` is already in `ItemLoggedFields`, so it reads like a hand edit) and count toward "items updated"; a row already spelled exactly like the *new* name gets neither, so 0 is a truthful result, not a failure.
  * **`Item.homeUnit` has FOUR write paths** — `detectHomeUnit` during import, the CSV's own `homeUnit` column passed through verbatim, item creation (`newItemSchema`), and hand edits — and only the first assigns `Unit.fullName` exactly. All four `.trim()`, so **case** is the only drift a rename/delete actually has to catch; the `btrim()` half is defence for legacy or direct-SQL rows, not a live path.
  * **The CSV import is the single source of truth for `homeUnit`, including on a MATCHED (already-existing) row, not only on create.** A matched row gets `homeUnit` written the exact same way a new one does — the CSV's own column verbatim when supplied, else `detectHomeUnit(effectiveDeviceName, ...)` where `effectiveDeviceName` is the CSV's `deviceName` when it supplied one, else the stored one — and it **overwrites** whatever was already stored, same as `deviceName`/`deviceUIC`/`deviceCategory`/the assigned user already do on a match. Routed through `loggedAfter` so it lands in `ItemEdit` like those fields, and inherits the RETIRED-gets-no-history rule. A CSV-column value does NOT count toward `detected` (only a `detectHomeUnit`-derived one does), and a row only lands in `unresolved` when it is *still* blank after both sources — i.e. the row had no stored value either, so leaving it alone (the "no effective device name" case) truly changed nothing.
  * **MDM WINS OVER A HUMAN on every importable field BUT ONE, and that is a decision — not an oversight.** (The exception, autogenerated device names, is the last sub-point below.) A technician's hand edit on `/i/<id>` or `/admin/items/<id>/edit` to `deviceName`, `homeUnit`, `deviceUIC`, `deviceCategory`, `storageLocation` or the assigned user is **reverted by the next import that carries a value for that field**. Confirmed on the 2026-08-11 production run: **14 of the 22 logged changes overwrote a previous human edit**, one of them made 3h44m earlier — a device reassigned to DCSIM (`W8APAA`, `PUBS STAL-01`) went straight back to `TROOP B 1ST SQUADRON 299TH CAVALRY REGIMENT` / `WX6YB0` / `NGHINB-299B-001`. Explicitly accepted 2026-08-10: MDM is the authority for all of them, so **corrections belong in Intune, not in this app.**
    - **The stakes changed when the import became nightly** (`/api/cron/import-drive`, 2026-08-10). Imports used to be run by hand, so a correction could stand for weeks; it now survives at most one night. The `Administrator` device-name edits of 2026-07-28 and 07-30 that the same run reverted show the tug-of-war was already running — it is simply much faster now.
    - **A partly-overwritten row can end up matching NEITHER source, and that is the shape to recognise when something looks wrong.** Blank CSV cells leave stored values untouched and `currentPosition` is not an importable column at all, so the device above kept the human's `currentUserEmail` + `currentPosition` while losing its name, unit and UIC. The record is not "MDM's" or "the technician's" — it is a mixture.
    - **THE ONE EXCEPTION (2026-08-11): an AUTOGENERATED device name is refused.** `isAutogeneratedDeviceName` (`import.ts`) matches `^BE-[A-Z0-9]{12}$` — the name an MDM re-enrolment invents. When MDM proposes one and the stored name is NOT autogenerated, `planImport` keeps the stored name and parks MDM's in `Item.mdmProposedName` (non-null = "rename this in Intune"; cleared automatically once MDM stops disagreeing). It withholds only where there is something better to keep: a stored name that is itself autogenerated, or absent, or a brand-new serial, all take MDM's name.
      **This is also the `homeUnit` fix, which is why it is one change and not two.** `detectHomeUnit` decodes the leading segment, so `BE-2AD6890X7IOL` resolved against a real production `Unit` row named `BE` and rewrote the device's home unit to `BE` — **18 devices were corrupted that way**, one of them from `Safety Office`. Withholding feeds the STORED name back into `effectiveDeviceName`, so detection runs against the good name again.
      The flag rides with the SILENT fields, never `loggedAfter`: it is the importer's note to a human, not a custody fact, so it must not reach `ItemEdit` — the same reasoning that keeps telemetry out of the history. Withholding likewise emits no history row for a rename that did not happen. The pattern is anchored and case-SENSITIVE deliberately: on the live export **91 of 1071 names carried the shape and every one matched it exactly**, whereas a looser `startsWith("BE-")` could refuse a genuine rename — the worse failure, since the flag would then ask someone to fix something in Intune that is already right.
    - **The worklist is `?needsRename=1` on `/items`, and like every other filter there it is implemented TWICE** — the Prisma `where` and `itemFilterSql` — because a sort involving a derived key takes the raw path. `items.readiness-sort.parity.test.ts` covers it both alone and combined with `?uic=`, so a filter that quietly ignored the other cannot pass by being equally wrong on both sides. It is ONE-WAY (a checkbox, `MenuToggle`, not a two-option select): unchecked means "no filter", never "only the devices that are fine", which is not a list anyone wants. `sortFilterSummary` appends `· Rename` while it is on — an active filter has to be legible with the menu shut, or the page silently shows 3 devices out of 1,200 and looks like the whole catalogue.
    - Beyond that one exception the argument still stands: `deviceName` really is MDM's fact (it is the machine hostname) whereas `homeUnit` / `deviceUIC` / holder are **custody** facts MDM cannot know. Widening per-field authority any further changes all three import front doors at once, so it needs an explicit decision.
  * **Consequence: `renameUnit`'s backfill is not permanent.** It fixes the fleet's spelling for every item matching the old name *at that moment*, but the next import that carries a `homeUnit` for one of those devices (CSV column or a re-run `detectHomeUnit`) overwrites it again — the importer, not the vocabulary, has the last word. This is accepted, not a bug, but the rename UI's "N items updated" success message describes only that moment, not a permanent guarantee.
  * **`learnUnits` is batched (3 queries) regardless of paste size** — it was a per-row upsert loop; keep it that way. The bulk-paste form on `/admin/units` reports malformed lines **by line number**, and saves nothing if any line fails to parse.
* **Readiness edits are ADMIN-only** and live in their own Server Actions — `markItemsReadyAction` (the "Mark as on hand" button, `admin/actions/items.ts`) and `setReadinessAction` / `setItemsCategoryAction` (the selection-bar controls, `admin/actions/readiness.ts`) — deliberately NOT folded into `updateItemDetailsAction`'s role-picked schema. That keeps the USER-editable field set exactly as narrow as it was (holder email + position only).
* **The readiness selector writes SIGNALS, not a state.** It is not a stored enum sneaking back in: `READY_TO_DEPLOY` stamps `markedReadyAt` (routed through the same `markItemsReady` the button uses, so the two cannot disagree), `UNTRIAGED` clears it, and `RETIRED`/`ACTIVE` set the `Item.status` lifecycle column. **`DEPLOYED` and `IN_REPAIR` are absent from the Zod target enum on purpose** — they are derived from an open unreturned receipt / MDM logon and from a `PENDING` `ServiceQueueItem`, so a POST asking for them is REJECTED, not ignored. Widening that enum is a security change; `admin/actions/readiness.ts` is security-sensitive for exactly that reason: update `docs/SECURITY.md` when you change it.
  * **Asymmetry to know:** `markItemsReady` skips `RETIRED` rows (asserting "back on my shelf" about kit that left the fleet is meaningless) but `clearItemsReady` does NOT — clearing *retracts* an assertion, and a retired row can carry a stale stamp that would read "Ready to deploy" the moment it is reactivated.
* **Bulk item writes are 3 queries, never one per item.** `setItemsCategory` does one `findMany` (id + current value only), one `updateMany` over just the changed ids, and one `createMany` of `ItemEdit` rows, in a single transaction — reusing `diffItemFields` so bulk history rows are shaped identically to hand edits, and writing no history row where nothing changed. Do NOT implement a bulk action as `updateItemFields` in a loop; that is the banned N+1 *and* one transaction per row.
* **The stale-device export is the dashboard's one WORK LIST, and its exclusions are the design.** `listStaleDevices` / `countStaleDevices` (`analytics.service.ts`) return devices whose parsed MDM logon (`Item.lastLogonAt`) falls **30-90 days** back — `STALE_MIN_DAYS`/`STALE_MAX_DAYS` in `analytics.types.ts`, half-open (`>= from`, `< to`) so exactly one boundary claims a device landing on it. Four things are deliberately NOT in it, and each answers a question this list is not asking: **past 90 days** (long-term lost kit — a different response, and folding it in buries the devices still worth chasing); **`lastLogonAt IS NULL`** (never enrolled, or an unparseable export date — that is "we cannot say when", not "45 days ago"); **RETIRED** (out of the fleet, like every other aggregate here); and **live custody** — a device on an OPEN receipt with an unreturned line is accounted for by that receipt, where MDM silence is expected. That last one embeds `CUSTODY_FROM`/`OPEN_CUSTODY_PREDICATE` from `custody.sql.ts` rather than restating the rule, so it means what the Readiness badge means.
  * **ONE predicate backs both the count and the rows** (`staleDeviceWhere`), because the card renders a number and the button fetches the sheet in a *separate* round trip — two copies would let the screen say 47 and the file carry 52. For the same reason `now` is computed in JS and **bound as a parameter**, never `now()` in SQL: a clock read independently per query lets a device cross the 30-day line between them, and an injected `now` is what makes the window testable at all.
  * The rows are built server-side and the **file is written in the browser** by the existing `downloadCsv` — one CSV writer in the app, and its formula-injection guard matters more on this sheet than on any other, since Device name, Holder and Last logon user all arrive verbatim from the MDM import. Bounded by `STALE_EXPORT_MAX` with a `+1` overflow probe, and a truncated export **says so**; the readiness column comes from `READINESS_CASE`, never from classifying rows in TypeScript.
* **Analytics is admin-only and re-queries on the server.** All dashboard state lives in the URL (`?uic=&range=`), so there is exactly one filtering implementation and it is the SQL one. The whole page is a fixed number of queries and does not grow with fleet size. The unit leaderboard is intentionally NOT scoped by the global UIC filter — it is how a user picks a unit.
* **Volume ("DA Form 2062 volume", `VelocityWidget` in code) counts ITEMS, not receipts.** A receipt can carry mixed categories, so counting receipts per category would double-count and the stack would not sum to the total. Also note closed receipts are purged after 90 days, so that series cannot see further back than the purge window — say so in the UI rather than hiding it.
* **Chart colours are validated, not taste.** See `src/app/admin/analytics/palette.ts`: re-run the validator against the ledger surface (`#fbfcf9`) before changing a hex. The audit-readiness donut is blue → yellow → red (audited / overdue / never) because any green-vs-red pairing fails colourblind separation — **do not "fix" it back to green.** Note the `/items` audit-dot colours (green/amber/slate) deliberately do **not** match it: they fail the validator as adjacent wedges, which small dots beside a text label survive and a donut does not. The per-chart **table view** is the documented mitigation for the under-contrast palette slots; do not remove it.

### 🤖 Service Queue (item-level)
* **Needs-service flag:** Items are placed in the service queue by a per-item "Needs service?" flag captured on the hand-receipt builder (per serial) or on the item detail page. Each flagged item carries a service type: **Reimage**, **Repair**, or **Other** (with a custom message stored in `serviceNote`).
  * **DCSIM-recipient only (builder):** on the hand-receipt builder the "Needs service?" control (the whole Service column) is offered **only when the recipient is DCSIM** — the queue is for kit coming in to the desk, not equipment issued to an outside customer. Same "completely hidden in UI **and** enforced server-side" pattern as the pickup button: `createReceiptAction` drops any `service[...]` selections when `receiver.isDcsim` is false, so a crafted POST can't enqueue. The **item-detail-page** flag is unaffected (no recipient there).
* **Item-level queue:** The queue holds one entry per item (`ServiceQueueItem`, unique `itemId`), and only items whose entry is `PENDING` appear. Each entry may be tied to the hand receipt it was flagged on (`transferId`), shown on the item detail page.
* **Mark Completed (reversible):** Removing an item from the queue sets its status to `COMPLETED` — the record is retained (never deleted) and drops off the active queue. It can be reopened to `PENDING` from the item detail page.
* **Queue view:** The `/admin/queue` view lists SN, Device Name, Unit (item home unit), Service Type, and Actions (View + Mark Completed), with search, service-type filter, sort, and user-toggleable columns.
  * **It is CAPPED at `QUEUE_MAX_ROWS` (200), deliberately NOT paginated.** `listActiveQueue` used to be a bare `findMany` with no bound, and the whole result is serialized into a Client Component — the "bound every list" rule. Pagination is the wrong shape here: production runs **9** pending entries, and `ServiceQueueTable` searches, filters and sorts in the browser, which is instant on a real queue and would become a server round-trip per keystroke. The cap makes the page's cost knowable without giving that up. It takes `QUEUE_MAX_ROWS + 1` purely as an overflow probe, so "is there more?" costs no second COUNT, and the probe row is trimmed before render. **If the cap is ever hit the page says so, and says that the search/filter/sort cover only the rows shown** — silently dropping rows there is a confident wrong answer about which devices need service. Raising the cap is fine; removing it is not.

### 🤖 Contact book — the hand-receipt auto-save
Filing a receipt saves each **non-DCSIM** party into the shared book (`upsertContactFromParty`, called best-effort from `createReceiptAction`), so the next receipt for that person autofills from the `ContactCombobox`. The authz side of this — it is the one non-admin write path — is summarised in `CLAUDE.md` §1 and specified in `docs/SECURITY.md` §2. The mechanics:
* **The party name is ONE free-text field and a `Contact` needs two columns.** `parsePartyName` (`contacts/party-name.ts`, pure leaf) is the only parser: the first comma wins (`"Doe Jr., Jane"` keeps the suffix on the surname), otherwise the FIRST token is the given name so compound surnames survive (`"Jane Van Der Berg"` → Jane / Van Der Berg). Anything that cannot make two non-empty halves — a one-word name, a missing email — is **skipped, never saved with a placeholder**. The known cost is two given names misfiling (`"Maria Jose Cruz"` → Maria / "Jose Cruz"). Do not add a second parser; `prisma/schema.prisma` says why the columns are split at all.
* **The name split is CREATE-ONLY, and that is a correctness fix, not caution.** The parse is lossy in one direction and *the builder's own autofill feeds it back in*: `ContactCombobox`'s `onPick` writes `` `${firstName} ${lastName}` `` into the single name field, so a curated "Mary Jo" / "Smith" returns as "Mary Jo Smith" and re-parses to "Mary" / "Jo Smith". Picking that contact and filing the receipt — with nobody typing a character — would silently refile a correct row. Typing the full name by hand does the same, so guarding `onPick` alone would not be enough. A contact's name therefore changes only by a deliberate admin edit on `/admin/users`.
* **The RECEIVER refreshes; the SENDER is create-only** (`refreshExisting`). The receiver is typed or picked fresh for this receipt, so it is the newest thing known about them. The sender's four fields are seeded on load from `senderPrefill` → `getLastReceiver` — the **frozen party snapshot on the item's open receipt**, which can be months old and is usually left untouched on a turn-in. Refreshing from it would revert an admin's correction using older data. Creating from it is still right: an outside person handing kit back who is not in the book yet is exactly who is missing.
* **Blank rank does not overwrite.** `partySchema` requires unit, contact and email for a non-DCSIM party, so those always refresh; `rank` can legitimately arrive empty, and a blank is likelier an omission than a correction, so it is omitted from the UPDATE (Prisma reads `undefined` as "leave this column alone"). An over-long rank is **dropped**, not rejected — losing a stray field beats losing the contact, mirroring the CSV importer. The cap is imported as `RANK_MAX_LENGTH` from `contacts.schema.ts`, never restated: a local copy that drifted below the schema's would turn the drop back into the refusal it exists to prevent.
* **The one-off backfill reuses the same function, and that is the point.** `backfillContactsFromReceipts` (`contacts/backfill.ts`, run by `npm run backfill:contacts`) seeds the book from parties on existing receipts by calling `upsertContactFromParty` per person — so the DCSIM skip, the create-only name and the email match key are one implementation and cannot drift. Receipts are scanned **oldest-first with a cursor** (not `skip`, which re-walks the offset on the fastest-growing table) and de-duplicated by email into one candidate per person, so **newest receipt wins** and someone on forty receipts costs one write, not forty replayed in the wrong order. Idempotent: a second run rewrites the same values. Dry run is the DEFAULT — `--apply` is required to write, because it targets whatever `DATABASE_URL` it is handed. Reachable history is bounded by retention, not by the function: parties who appear only on receipts closed more than 90 days ago were already purged.
* **Best-effort, and it must stay that way.** The receipt is filed and authoritative before this runs, so a failure is logged and never surfaced, like the draft-cleanup / service-queue / email blocks around it. **The caught error is NOT serialized** — a Prisma validation error embeds the offending arguments, which here are the party's name, unit, phone and email. Only the role, the error name and any Prisma code are logged, so party PII stays out of the server logs; `receipts.test.ts` asserts across *every* `console.error` argument, because checking the format string alone cannot catch a leak in the second one.
