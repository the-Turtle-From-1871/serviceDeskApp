# Bulk rename with a numbering sequence — design

**Date:** 2026-08-11
**Status:** approved, not yet implemented
**Depends on:** PR #119 (`2026-08-11-bulk-actions-on-a-scanned-batch`) — this lives in the
More-actions sheet that branch adds. **Dependency satisfied:** #119 merged as `e84897a`, so
build on `main`. Branch `worktree-bulk-rename` is cut from it.
**Surface:** the `/items` selection bar's More-actions sheet, plus one pure module, one
service function and two Server Actions.

## Problem

Renaming devices to a convention is a per-item edit today: open `/i/<id>` or the admin edit
page, type a name, save, repeat. A shipment of forty laptops that needs `LAPTOP-001` through
`LAPTOP-040` is forty round trips through two screens.

The natural worklist already exists — `/items?needsRename=1` lists devices whose MDM name is
an autogenerated `BE-XXXXXXXXXXXX` that the importer refused to apply — and the selection
that feeds a bulk action already exists. Nothing connects them.

## The accepted tradeoff — read this before changing anything here

**`deviceName` is MDM-owned, and the nightly import reverts a rename within a night.**
`import.ts` applies the CSV's `deviceName` to every matched serial; `/api/cron/import-drive`
has run nightly since 2026-08-10. On the 2026-08-11 production run, **14 of 22 logged changes
overwrote a previous human edit**, one made 3h44m earlier.

This was raised with the user, who chose to build it in the app anyway. It is a stated
assumption, not an oversight, and **it is not to be re-litigated in review**. Two
consequences follow and both must be visible to a reader:

1. The `CHANGELOG.md` entry MUST say the names revert at the next MDM sync. A rename button
   whose release note omits that is the one genuinely misleading thing this feature could do.
2. `deviceName` is in `ItemLoggedFields`, so each rename writes an `ItemEdit` row and the
   nightly revert writes another. Two hundred devices is roughly 400 history rows a day.
   Storage is not the concern — `ItemEdit` retention was measured against the database
   ceiling and explicitly rejected as a problem. **History legibility is the cost**: an
   item's edit log fills with rename churn. See the `#114` interaction below, which turns
   part of that churn into something useful and puts one real bound on it.

### The `#114` interaction — mostly a gift, with one bound to respect

`#114` (`0beffeb`, merged after this design was drafted) added `deriveNameHistory`
(`name-history.ts`, pure) and a **"Previous names"** disclosure on the item page. It answers
"what do I rename this back to?" by finding **the most recent `deviceName` change whose
`from` is a real name**.

That composes *well* with bulk rename, which is worth stating because the churn above sounds
purely negative. The cycle is: you set `LAPTOP-001`, the nightly import reverts it to
`BE-7J5AKRNFLP6B`, and the revert's `ItemEdit` row records `from: LAPTOP-001`. The disclosure
therefore surfaces `LAPTOP-001` as the name to type back into Intune — which is exactly the
name you chose. **The revert this feature's tradeoff accepts is what makes the answer
correct.** Do not "fix" the churn by suppressing rename history; the disclosure depends on it.

The bound to respect: `deriveNameHistory` reads only the **25 newest `ItemEdit` rows** for an
item, deliberately, so a long-lived item does not ship its whole audit trail into the RSC
payload. A device in a bulk-renamed batch accrues ~2 rows a day from rename-plus-revert
alone, so that window is consumed in under a fortnight. Consequences: `deriveNameHistory`
still answers its own question (it scans for `deviceName` changes and those are the rows
filling the window), but **other** edits — holder, unit, category — fall out of the 25 sooner
for any device that has been bulk renamed. Nothing here changes that bound; it is recorded so
the next person to widen the window knows what is filling it.

Also note `#114` **reversed `mdmProposedName` from silent to LOGGED** (same day it shipped
silent), because the disclosure needs the superseded proposals. This design still writes
nothing to that column, so nothing changes for us — but any future edit here must not assume
it is telemetry.

The durable fix is renaming in Intune, which is what `mdmProposedName` and the
`?needsRename=1` worklist already point at. This feature does not replace that.

## Non-goals

- No change to `import.ts`, and no attempt to make `deviceName` app-owned. That inverts a
  stated authority rule and touches all three import front doors — a separate decision.
- No free-form template syntax with a `{n}` placeholder. Prefix + hyphen + number only.
- No export of the generated names for pasting into Intune. Considered and declined.
- No new route. The control lives in the existing sheet.
- No change to `mdmProposedName` or the `?needsRename=1` worklist (see below).

## What changes, from the operator's side

Select or scan a batch, open **More actions**, and the sheet gains a Rename section: a
**prefix** field and a **start at** field. As you type it shows the range it will produce and
refuses to apply if any generated name is already taken:

```
Rename — prefix
[ LAPTOP              ]
Start at
[ 001 ]

200 devices, in scan order:
  LAPTOP-001 … LAPTOP-200

⚠ 2 names already taken:
  LAPTOP-005 (7XK2Q13)
  LAPTOP-118 (4NN8P02)

[ Rename 200 ]  (disabled)
Change the prefix or start number to continue.
```

Devices are numbered in **selection order** — the order you scanned or clicked them — so the
numbers match the order of the pile in your hands.

## Architecture

### 1. `rename-sequence.ts` — the pure leaf

`src/modules/items/rename-sequence.ts`. No DOM, no network, no Prisma, so it unit-tests
directly — the same convention as `readiness.ts`, `swipe-row.ts` and `recipient-search.ts`.

```ts
buildRenameSequence(count: number, prefix: string, start: string): string[]
```

- **Pad width is inferred from `start` as typed**: `001` → three digits, `01` → two, `1` →
  one. The input is a string precisely so `001` and `1` can mean different things; parsing it
  to a number first would throw the width away.
- **Width is a MINIMUM, not a ceiling.** Start `95` with ten devices yields
  `95, 96, 97, 98, 99, 100` — it grows rather than refusing or wrapping. That is how a person
  reads a numbering scheme, and refusing would be a puzzle at the moment of use.
- Prefix is trimmed. The separator is a literal hyphen.
- Rejects: a blank prefix, a `start` that is not digits only, a non-positive count.

### 2. One computation, two callers — and the server never trusts the client's

The client calls `buildRenameSequence` to render the live range line as you type. The server
calls **the same function** to produce the names it writes.

**`renameItemsAction` takes `(itemIds, prefix, start)` and recomputes the sequence itself. It
must never accept a name list from the client.** A client-supplied list would turn an
admin-gated action into "write any string to any item" — and `deviceName` is deliberately
kept in the admin-only `editableItemFields` set so it is not reachable that way. A test pins
this by posting an extra `names[]` and asserting the recomputed values are what land.

**The array order of `itemIds` IS the numbering.** It is load-bearing input, not incidental
ordering. `getItemsByIds` already establishes the "preserve the caller's order" precedent.

### 3. Two Server Actions, both `requireCapability("MANAGE_ITEMS")`

`deviceName` lives in `editableItemFields` — the admin field set — so `MANAGE_ITEMS` is the
gate, matching `setItemsCategoryAction` rather than the `MANAGE_QUEUE` readiness actions.

| Action | Returns | Role |
| --- | --- | --- |
| `previewItemRenameAction(itemIds, prefix, start)` | `{ names, collisions }` | Advisory — drives the range line and the collision list |
| `renameItemsAction(itemIds, prefix, start)` | `{ error } \| { ok, renamed, unchanged, skipped }` | Authoritative — re-checks collisions **inside the transaction** |

Preview is a hint; the transaction is the boundary. That closes the window where another
session takes one of the names between your preview and your tap.

Result shape is annotated as a local `type`, not inferred — a `"use server"` module may only
export async functions.

### 4. `renameItems` — the service

`src/modules/items/items.service.ts`. Enforces **no** permissions; the action owns the guard.
Caps at `MAX_BULK_ITEMS` as the backstop. One transaction, four queries:

1. `findMany` the **ACTIVE** ids, `select: { id: true, deviceName: true }` — the current name
   is needed for the history rows.
2. **Collision check** — parameterized `$queryRaw` using `lower("deviceName") = ANY(...)`,
   excluding the ids being renamed.
3. The batched `UPDATE`.
4. `createMany` the `ItemEdit` rows.

**Retired items are excluded and reported**, matching the rule the previous branch wrote into
three docs. They cannot reach here through the UI — `selectableIds` excludes them and
`addMany` refuses them — but a crafted POST or an item retired mid-flow can. **The survivors
are then numbered CONSECUTIVELY**, so eight active items out of ten selected get `001…008`,
not `001…010` with holes at 5 and 7. Gaps would be worse than a shifted sequence: the labels
are printed and the pile is physical.

**`mdmProposedName` is untouched**, so a renamed device stays on `?needsRename=1`. That flag
means "MDM still calls this `BE-XXXXXXXXXXXX` — fix it in Intune", which a local rename does
not change. The importer already clears it automatically once MDM stops disagreeing, so it
resolves itself the moment the real fix lands.

### 5. The write — N different values in one statement

`updateMany` sets ONE value across every matched row, so a rename cannot use it:

```sql
UPDATE "Item" SET "deviceName" = v.name
FROM (VALUES (${id}::text, ${name}::text), …) AS v(id, name)
WHERE "Item"."id" = v.id
```

Values are **bound**, never interpolated (CLAUDE.md §2).

**This is deliberately NOT a second copy of the importer's batched UPDATE.** That one splices
column *identifiers*, which is the entire reason it carries `UPDATABLE_ITEM_COLUMNS`,
`FIELD_TO_COLUMN` and `COLUMN_CAST`. Here the column is the literal `"deviceName"` — there is
no dynamic identifier, so none of that machinery applies and the statement is materially
smaller and safer. Do not "unify" the two; the importer's complexity is not shared.

**No chunking.** The importer chunks at 500 rows × 15 columns; this binds two parameters per
row and `MAX_BULK_ITEMS` is 500, so 1,000 parameters against Postgres's 65,535 ceiling. One
statement always suffices.

**Case-insensitive collision matching.** `deviceName` is NOT citext — unlike
`serialNumber` — so a plain `in` would treat `LAPTOP-005` and `laptop-005` as different names,
which no one reading the property book would. `lower()` on both sides mirrors how
`units.service.ts` already compares unit names. It is a sequential scan (`deviceName` carries
no index at all), which is fine against ~1,200 rows; revisit only if the fleet grows an order
of magnitude.

**History reuses `diffItemFields`**, so bulk rename rows are shaped identically to hand edits
— the same thing `setItemsCategory` does. A device already holding its target name produces
no `ItemEdit` row and is reported as `unchanged`, not `renamed`.

### 6. The sheet

A Rename section in the existing `BulkActionsMenu`, inheriting its popover rules unchanged
(no layout class on the `[popover]` element; `useDismissSwallowsTap`; the id already in all
four `globals.css` rule groups). It follows that component's established shape: its own
`useTransition`, the selection NOT cleared after applying, and the outcome line naming counts.

The preview is a **compact summary**, not a row-per-device table: the first name, the last
name, the count, and any collisions listed explicitly. Nobody audits 200 rows to catch a
mistake — a wrong start value is visible in the range line alone, and a 200-row scrolling
list inside a bottom sheet is the growth the styling rules already warn about.

## Error handling

| Case | Behaviour |
| --- | --- |
| A generated name is taken by another device | Whole batch refused, nothing written; clashing names and their serials named |
| Blank prefix, or a `start` that is not digits | Zod refuses with a readable message |
| Over `MAX_BULK_ITEMS` | `ItemError("TOO_MANY")`, readable message in the action |
| Item retired between preview and apply | Skipped and counted; survivors numbered consecutively |
| Device already holds its target name | No write, no history row, reported as `unchanged` |
| Duplicate within the generated batch | Impossible by construction — consecutive integers |
| Client posts its own name list | Ignored; the server recomputes from `(itemIds, prefix, start)` |
| Anything else | `console.error` server-side, fixed generic string to the client |

## Testing

**Pure — no DB, no jsdom.** This is where the bugs would be.
- Pad width inferred from the start value (`001` vs `01` vs `1`).
- Width is a minimum: start `95`, ten devices → `95…99`, then `100`.
- Prefix trimmed; blank prefix, non-digit start and non-positive count all rejected.

**DB — `renameItems`.**
- N distinct names land, in one statement, in selection order.
- A collision refuses the whole batch and writes **nothing** — assert the items are unchanged.
- Retired excluded, counted in `skipped`, survivors numbered consecutively.
- A device already holding its target name writes no `ItemEdit` row and counts as `unchanged`.
- History rows match the shape hand edits produce.
- Over-cap throws `TOO_MANY`.

**Actions — the security layer.**
- Both refuse without `MANAGE_ITEMS`, **with the guard mocked to reject.** Three vacuously
  passing capability tests shipped on the previous branch because the shared `beforeEach`
  resolves the guard; a `.rejects` assertion with nothing to catch passes while asserting
  nothing.
- **`renameItemsAction` ignores a client-supplied name list.** Post `names[]` alongside the
  real fields and assert the recomputed values are what land. This is the security property
  of the feature.

**jsdom.** The range line updates as fields change; Apply is disabled while a collision is
listed. jsdom implements no Popover API, so the sheet's open/dismiss/anchoring are NOT
covered here — they are already proven for this component and unchanged by this work.

## Risks

- **The feature's output is temporary by design.** Everything above is honest about it, but
  the first person to use it and then look the next morning will be surprised regardless. The
  changelog line is the mitigation and it is not optional.
- **Numbering depends on selection order**, which is insertion order in the persisted
  selection array. If that array's ordering guarantee is ever weakened — a `Set`, a sort, a
  dedupe that reorders — the numbers silently stop matching the physical pile. Worth a
  comment at the point the order is consumed.
- **No index on `deviceName`.** The collision check is a sequential scan. Correct now, and
  the first thing to look at if `/items` slows after this ships.
- **A bulk-renamed device consumes its 25-row `deriveNameHistory` window in under a
  fortnight**, at ~2 rows a day from rename-plus-revert. The "Previous names" disclosure keeps
  working — those rows are the ones it reads — but older non-rename edits drop out of that
  window sooner on renamed devices than on untouched ones. Recorded rather than fixed; see the
  `#114` section.
